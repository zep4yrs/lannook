# 移动端浏览器连接 TLS/加密传输 —— 技术评估报告

> 范围：为 LanNook 的移动浏览器连接（扫码 → HTTP/WS → 文件互传）增加 TLS/加密传输的方案、成本与风险评估。
> 结论先行：**推荐「快速模式（HTTP 明文，默认）+ 安全模式（HTTPS/WSS，可选开关）」的混合方案**，安全模式用 rustls + 本地持久化自签名证书，与现有服务**同端口**（协议嗅探）部署；明确否决「强制安装根证书」作为主路径。总工作量约 **1.5–2 人周**。
> 日期：评估基于当前 main 分支代码（v26.3.0 面板）。

---

## 1. 现状摘要

**服务端（Tauri 2 + axum 0.8）**

- `src-tauri/src/server/mod.rs`：`axum::serve` 绑定 `0.0.0.0:{port}`（默认 `53317`），纯明文 `TCP + HTTP/1.1`。路由 = `/api/*`（REST）+ `/ws`（WebSocket 升级，token 走 query）+ SPA fallback + PWA 资源。`AppState` 持有 `connection_token`（UUID v4，**每次进程启动重新生成**）、`desktop_control_token`（不进 URL）、`port`、`local_ip` 等。
- 连接地址/二维码生成有两处独立格式化 `http://{ip}:{port}/mobile?token={token}`：`server/mod.rs::local_url()/qr_url()` 与 `commands/server_cmd.rs::connection_url()`（`get_connection_info`、`get_connection_qr_code`、`get_connection_diagnostics` 都在用）。
- WS 认证：`/ws?token=` 校验 `desktop_control_token`（桌面控制通道）或设备 `session_token`；未审批/过期审批一律 401。另有 `MAX_WS_CONNECTIONS=512`、每设备 4 个会话的限制。
- 加密现状：grep 全仓没有任何 rustls/rcgen/native-tls/TLS 相关代码，纯明文。README「安全边界」已明确披露这是已知设计边界。

**前端**

- REST 基础地址 = `window.location.origin`（`src/services/api.ts`）→ **页面是 https 时所有 fetch 自动变 https，零改动**。
- 移动端 WS 地址（`src/stores/mobileSession.ts:313`）：`window.location.protocol === "https:" ? "wss:" : "ws:"` → **已经按页面协议自适应 wss，无需改动**。
- 桌面控制 WS（`src/stores/app.ts:258`）固定 `ws://127.0.0.1:{port}/ws?token={controlToken}` → **纯回环，可保持明文**（回环地址在浏览器安全上下文规范中是 "potentially trustworthy"，https 页面连 `ws://127.0.0.1` 不构成 mixed-content 拦截；同时避免桌面 WebView 处理自签名证书信任的所有麻烦）。
- 二维码刷新对比（`src/utils/connectionQr.ts`）按完整 URL 字符串比对 → 协议变更时需同步。
- CSP（`server/mod.rs` 的 SPA fallback 头）已是 `connect-src 'self' ws: wss:` → 已允许 wss，无需改。

**认证/配对现状（对方案评估很重要）**

- 二维码 URL 携带一次性配对 token（连接能力，每次启动轮换）；浏览器注册设备 → 获得 `session_token`，后续全部走 `Authorization: Bearer`（下载 token 也不进 URL）。
- 桌面默认审批接入、单次/信任设备两种授权、`authorizationExpiryHours` 可配置、6 位 PIN 配对（5 分钟过期 + 每 IP 锁定）、一次性授权随服务停止失效。
- mDNS 服务类型是自定义 `_lannook._tcp.local.`（非标准 `_http/_https`），广播 IP + 端口 + 设备名。
- Windows 防火墙规则按「程序 + 单 TCP 端口 + LocalSubnet」用 netsh 建立，诊断脚本按端口查规则。

## 2. 威胁模型

按 README 定位，LanNook 面向**可信局域网**；本评估明确的主要对手：

| 对手 | 能力 | 对明文 HTTP/WS 的实际威胁 |
| --- | --- | --- |
| **同网被动嗅探者**（主对手） | 在同一 Wi-Fi/有线网上抓包；开放网络直接可嗅，WPA2 共享 PSK 下持 PSK 者可解密 | **直接致命**：明文可见全部文件分块内容、文件名、大小、进度、会话 token、QR 配对 token |
| 主动中间人（ARP 欺骗/伪造热点/DNS 劫持） | 拦截并可改写流量、可注入伪证书 | 明文下可窃听+篡改；TLS 下若用户点过了证书警告则仍可被中间人（见 §6 风险 2） |
| 获得二维码/地址的外部人员 | 拿到配对参数直接接入 | 由现有审批/PIN/token 机制覆盖，**与 TLS 正交** |
| 同机攻击者（能读桌面磁盘的本地进程/用户） | 读取 APPDATA | 可读私钥文件获 MITM 能力；威胁模型内通常视为不可防（桌面即用户本体） |

**关键区分**：现有 token/审批机制解决的是「**谁可以连接**」（授权/接入控制）；对「同一网络被动嗅探者」这类对手，它们解决的是「**传过去的内容是否保密**」——而明文下内容完全不保密。token 轮换只缩短「可重放直连」的时间窗，**不减少被窃听的字节**。

## 3. 候选方案对比

| 方案 | 浏览器信任 UX | Tauri 侧实现成本 | 主要风险 | 结论 |
| --- | --- | --- | --- | --- |
| **(a) rustls + 本地自签证书 + 首次「继续访问」** | 首次必经证书警告：iOS Safari「此连接不是私密连接 → 显示详细信息 → 访问此网站」；Android Chrome `NET::ERR_CERT_AUTHORITY_INVALID` → 高级 → 继续前往；**异常按会话记忆**，刷新/重开会重复出现。`wss` 需在页面级绕过后同源可用（iOS 各版本行为有差异，需真机矩阵验证）。 | M（中）：rcgen 生成证书、rustls/axum-server 接 TLS、URL 生成切换 https/wss、诊断加 TLS 探针 | 证书信任 UX 是全方案最难的点；绕过后用户无法感知是否被 MITM（除非比对指纹，见 §7）；证书过期/无正确 SAN 时 iOS 部分版本**不提供绕过** | **可行，作为安全模式的内核**（配合持久证书把频次降到「换设备/清站点数据」级别） |
| **(b) 每次启动生成临时证书** | 每次启动所有手机都要重新绕过一遍，站点异常记忆全部失效 | 比 (a) 少一个「持久化」步骤 | UX 最差；指纹变化让用户永远无法建立任何习惯性信任 | **否决作为主方案**；仅在 (a) 的退化兜底里使用（磁盘不可写时临时生成） |
| **(c) 让用户在手机安装根证书** | 极重：iOS 需「下载描述文件 → 设置 → 通用 → 关于本机 → 证书信任设置 → 开启完全信任」两步以上；Android 需「设置 → 安全 → 安装证书」且个别厂商 ROM 路径不同；对普通用户是**高危操作**（在私人设备植入根 CA） | 低（服务器实现同 (a)），但交付了「让用户安装根 CA」的长期运维负担（过期、撤销、换机） | 安全风险高（用户被引导在手机装根 CA，习惯一旦养成会被钓鱼利用）；iOS 明确要求额外开启「完全信任」开关，一次错过就是死路 | **直接否决作为主路径**；可留作「高级选项」远期再议，本评估不建议排期 |
| **(d) 混合：HTTP 明文默认「快速模式」+ HTTPS/WSS 可选「安全模式」开关** | 默认路径零回归（现状不变）；安全模式复用 (a) 的信任流程，但用户是**显式主动开启**，可配合应用内引导文案 + 证书指纹展示降低惊吓度 | M（中）：在 (a) 之外加模式开关、设置项、双模式状态机、UI 文案 | 状态机复杂度（模式切换、失败回退）；需保证快速模式永不被安全模式误伤 | **推荐**：不伤害现有默认体验，守住 README 现有定位，同时给需要保密性的用户一条明路 |

**浏览器兼容性关键事实（按 2025 年主流行为）**

- **iOS Safari**：自签名 → 拦截页有「显示详细信息 / 访问此网站」路径，**异常按会话有效**；`wss://` 在文档级绕过后同源可用，但 iOS 历代对「绕过后发起的 WebSocket 握手」偶有二次拦截或失败，必须上真机矩阵；**证书过期或 SAN 不含所访问主机名/IP 时，部分 iOS 版本不提供「继续访问」入口** → 证书必须长生（建议 10 年）+ 正确 SAN（含所有本机私有 IP 与 `*.local` 主机名）。不支持「安装根 CA 后无感」（仍要走「完全信任」开关）。
- **Android Chrome**：`NET::ERR_CERT_AUTHORITY_INVALID` → 高级 → 继续前往，**会话级**放行；同源 `wss` 可用；Chrome 已移除「永久例外」。对 IP 直连 + IP SAN 支持良好。
- **Android/桌面 Firefox**：有「接受风险并继续」且**持久记忆例外**，是三家里对自签名最宽容的（也是协议嗅探同端口部署下最容易测试的）。
- **同端口方案特殊价值**：安全模式与快速模式共用端口时，网址除 `http→https` 外**端口、路径、token 全不变**，二维码密度、防火墙规则（按端口）、连接诊断、mDNS（按端口）全部免改动。

## 4. 推荐方案与渐进路线

### 4.1 推荐架构（明确立场）

> **产品形态 = (d) 混合双模式；安全模式的技术内核 = (a) 持久化自签证书 + rustls 同端口 TLS。**

- **默认**：快速模式（现状明文 HTTP/WS，零回归，README 定位不变）。
- **安全模式（可选设置项）**：服务启动时用 `rcgen` 生成/加载 **10 年有效、SAN 覆盖全部私有接口 IP + `{hostname}.local`** 的自签证书（PEM 存于 APPDATA，先存在则复用，不随启动轮换），用 rustls（TLS 1.3，开 session resumption）+ **与快速模式同一端口**的双协议监听（TCP accept 后嗅探首字节：`0x16` → TLS，否则 HTTP，约 100 行自定义 `Listener` 封装 axum `serve`）；二维码/连接地址输出 `https://`、移动端 WS 自动 `wss://`；桌面控制通道保持 `ws://127.0.0.1` 原样。
- **同端口设计理由**：现有端口是「设置项 + 防火墙规则 + 诊断 + mDNS」的单一锚点。同端口嗅探把 TLS 接入的涟漪压到最小；若团队不想要自定义 accept 嗅探，退路是**双端口**（TLS 用 `port+1`），代价是防火墙第二条规则 + 诊断/mDNS/地址选择器多一个端口，工作量约 +0.5 人日，评估仍通过。
- **信任流程设计（最难 UX 点的解法）**：
  1. 用户显式开启安全模式 → 面板展示当前证书 SHA-256 短指纹 + 「手机上浏览器首次会提示『不安全』，**这是预期行为**」的引导文案（中英双语）。
  2. 手机扫码打开 `https://ip:port` → 浏览器证书警告 → 用户按引导文案逐条点过（iOS/Chrome/FF 各有「高级/详细信息」路径，引导页给出分平台截图式说明）。
  3. 首次成功进入后，提示「已加密连接 🔒」，**如与面板指纹一致**可在界面展示「连接已加密，指纹与电脑一致」的确认徽标；不一致时显示警示。（注：浏览器无 JS API 读取对端证书，指纹只能人工比对——这个诚实限制写进文档与引导文案。）
  4. 证书持久化 ⇒ 同一手机后续会话一般不重复警告（浏览器会话级例外 + 站点数据被清才重来）。

### 4.2 渐进路线（两阶段）

| 阶段 | 内容 | 工作量 |
| --- | --- | --- |
| **阶段 1（最小可用，保 UX 下限）** | 设置项 `secureMode`；rcgen 生成持久证书（含 IP + `.local` SAN）；rustls + 同端口嗅探双协议监听；URL 生成 `https/wss` 切换（Rust 三处 + `connectionQr.ts` 刷新比对）；桌面控制通道不动；诊断加 `tlsEnabled`/指纹/`tlsProbeReachable`；mDNS 增加 `tls=1` TXT（可选）；失败自动回退快速模式并提示 | 约 5–7 人日 |
| **阶段 2（体验打磨）** | 安全模式引导页与分平台文案（i18n 双语）；指纹展示与「一致✓/不一致⚠」UI；真机测试矩阵固化进 CI/文档；Firefox 例外持久化验证；低端安卓 TLS1.3 性能与重连压测；README 安全边界更新 | 约 3–5 人日 |

## 6. 风险与缓解

| # | 风险 | 等级 | 缓解 |
| --- | --- | --- | --- |
| 1 | **证书信任 UX（最高风险）**：用户被浏览器「不安全」页吓到，误以为中毒/被钓鱼；iOS 各版本绕过路径与 `wss` 行为不一致 | 高 | 应用内分平台引导文案 + 指纹展示 + 「这是预期行为」明示；证书持久化降低重复警告；真机矩阵（iOS Safari 为最重测试锚点）；不做「泛泛劝用户忽略」的文案，只解释本场景 |
| 2 | **主动中间人 + 绕过后的 TOFU 局限**：用户点「继续访问」后，攻击者若抢先注入伪证书，用户无感知 | 高（认知诚实问题） | 报告与文档明确写出：安全模式防**被动嗅探**，对**主动 MITM 提供的是 TOFU（首次体验）而非强认证**；引导用户可选比对面板指纹；配对 PIN（带外信道）可作后续增强方向；不夸大 |
| 3 | **失败回退**：rcgen 失败、TLS 端口异常、iOS `wss` 拒绝 → 手机卡死 | 中 | 快速模式监听**始终保留**；安全模式任何初始化失败 → 显式回退快速模式 + 面板提示「安全模式不可用（原因），已回退快速模式」；诊断页一键排查 |
| 4 | **性能开销**：低端安卓 TLS 握手 + 全量分块过 TLS | 低 | LAN 场景 CPU 通常不是瓶颈；TLS 1.3（1-RTT 握手）+ session resumption 压低重连成本；512 KiB 分块流式加密封装开销可忽略；阶段 2 做低端机压测确认 |
| 5 | **调试难度**：浏览器证书拦截被误报为「连不上」 | 中 | 诊断页区分「TCP 可达 / TLS 握手可达」两档，新增 `tlsProbeReachable` 与证书指纹字段；日志明确标注 TLS 分支 |
| 6 | **私钥明文落盘**：APPDATA 中 PEM 私钥可被同机读取 | 中（威胁模型内可接受） | 权限设为 0600；README 说明「桌面操作系统本身是信任边界」；证书仅自签、无 CA 能力，损害面有限 |
| 7 | **兼容性脆点**：证书过期/无正确 SAN → iOS 不给绕过入口 | 低（做对了就低） | 10 年有效期 + SAN 覆盖全部本机私有 IP 与 `.local`；网卡变更时按需重签（判断依据：当前 SAN 集合与激活接口不符） |
| 8 | **双模式状态机回归**：安全模式开关后快速模式被误伤 | 低 | 单元测试覆盖 URL 生成两模式、连接自检两模式；真机回归矩阵把快速模式设为基线 |

## 7. 「不加密时的缓解项是否够用」结论

**不够。** 现有缓解项（启动即轮换的配对 token、默认审批、6 位 PIN + 每 IP 锁、授权到期、一次性授权、下载 token 走请求头）全部属于**接入控制/授权**层面，解决的是「谁可以连」；而威胁模型的主要对手——**同一网络的被动嗅探者**——**根本不需要通过认证**：在明文 HTTP/WS 上，文件分块内容、文件名、元数据、以及 token 本身都直接暴露在抓包里。缩短 token 有效期、加强授权提示可以缩小「可重放直连」的窗口、降低误接外部设备的概率，但**对被窃听的内容保密性没有任何帮助**。

因此：

- 若产品的安全承诺包含「在同一网络（尤其在公共/开放 Wi-Fi）上传文件不被旁观者读取」，**TLS 是必要项**，本报告推荐的安全模式即为此而设。
- 若产品保持 README 现有定位（「只在你信任且没有陌生用户接入的网络中使用」），则明文快速模式 + 现有授权机制在**该定位的威胁模型内**是可以接受的基线——这正是推荐的混合方案得以成立的理由：**默认不改变定位，安全模式把保密性交给想要它的用户**。
- 对「主动中间人」这一更强的对手，仅 TLS + 默认绕过仍不足（TOFU 缺陷，见风险 2）；真正的强认证需要带外通道（如 PIN 配对或指纹比对），建议列为后续增强而不是本方案 v1 的承诺范围。
